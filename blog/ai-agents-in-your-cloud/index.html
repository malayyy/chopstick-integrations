Where should your business AI agent run?

For some organisations, deploying an AI agent inside their own AWS, Azure or Google Cloud environment is the right architectural starting point.

CHOPSTICK INTEGRATIONS · 6 min read · 7 NOVEMBER 2026

An AI agent may read business records, call internal APIs, create tasks, retrieve documents or trigger workflows. Its runtime environment affects identity, network access, logging, data boundaries and operational ownership.

Start with data and access

Map which systems the agent needs, what it may read, which actions it may perform and who approves consequential actions. Use scoped service identities, least-privilege permissions and explicit tool allowlists.

Deploying in a customer's cloud

A deployment in AWS, Azure or Google Cloud can align the agent with existing identity, networking, secrets management, monitoring and governance. The right architecture depends on the cloud, model provider, data sensitivity and integration requirements.

Separate reasoning from execution

Keep model orchestration separate from business actions. Validate inputs, enforce schemas, check permissions at the API boundary and require human approval for sensitive operations. Use queues for long-running work and idempotency controls for retryable actions.

Make it observable and recoverable

Log tool calls, outcomes, latency and errors without indiscriminately storing sensitive prompts or records. Define timeouts, retries, escalation paths and a kill switch. Test prompt injection and untrusted document handling.

Running in a customer's cloud is not automatically secure. Security comes from identity, permissions, network design, data handling, monitoring and operational controls.

Build for the workflow, not the demo

Start with one bounded workflow, measure accuracy and exception rate, then expand permissions and autonomy only when evidence supports it.
